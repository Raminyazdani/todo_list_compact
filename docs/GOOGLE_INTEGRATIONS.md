# Google and calendar connections

The build's connected Google Drive tool successfully read the owner's live source. The coordinator also authenticated the native Google Calendar connector and observed two calendar sources. These are real connector reads inside the build chat. Neither connector grant is transferred into the deployed app or treated as an app OAuth refresh token. `server/integrations/google.ts` provides a scoped read-only adapter and truthful disconnected capabilities until an app-specific user grant is configured. Tokens never enter browser bundles, logs or public Git. The adapter offers metadata, bounded ledger cells, paginated calendar lists/events and all-day normalization. It has no source write, file-move or Calendar write method.

An owner must configure `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, approved callback origins and an encrypted owner-bound OAuth grant through an implemented consent flow before app sync can be enabled. Merely filling those variables is insufficient. Current connector discovery and a working local adapter do not prove deployed OAuth sync. Calendar writes remain unavailable until explicitly supported and authorized.

`server/integrations/calendar-runtime.ts` selects the configured owner's account and verified actor, checks the exact stored and refreshed `calendar.readonly` scope, and asks Better Auth to decrypt/refresh the grant on the server. Lists and events use read-only provider calls, stable hashed external IDs and owner-bound source status. Google responses are bounded to 2 MiB; pagination and returned events are bounded. A source failure records a generic code while retaining the last success time. Private feed URLs, tokens and upstream response contents are excluded from status/errors. Explicit local/iCal selection does not require a separate working Google grant. Independent orchestration contracts mock OAuth/database/transport; the live application grant is still NOT_CONNECTED.

## Read-only iCalendar

`fetchIcalFeed` accepts HTTPS on an exact configured host allowlist. It denies URL credentials, arbitrary ports/IP hosts, all nonpublic DNS addresses and redirects; HTTPS is pinned to the verified public DNS result. Read time/byte bounds are enforced. Private iCal URLs are secrets. Errors do not log URLs or credentials. `parseIcal` reads VEVENT, RRULE/RDATE/EXDATE and exception events, exclusive all-day end, embedded timezone definitions and default Berlin floating times. Expansion is bounded. Event text/attachments cannot invoke commands.

`expandRecurrence` evaluates local recurrence clock time and resolves each occurrence using its actual IANA offset. A spring DST gap is skipped for a generated recurrence instance; manually entered gap times are rejected. Ambiguous manual autumn times require earlier/later choice. All-day events remain local calendar days; task deadlines remain separate from events/time logs. The app must not create external events from a task date automatically.

## Holidays, hours and exports

`holidaysForYear` and `dayFlags` adapt the MIT Work Planner implementation while retaining the license notice. Current recurring German rules are used, with national/state/municipal scope and TH+BY/Pöcking union. One-off/historical/employer-specific days off are not inferred. The source legislation and calendars were read on 2026-10-13: [Bundesbank](https://www.bundesbank.de/de/aufgaben/unbarer-zahlungsverkehr/target/feiertagskalender-2026-749314), [Bavarian law](https://www.gesetze-bayern.de/Content/Document/BayFTG/true), [Brandenburg law](https://bravors.brandenburg.de/gesetze/ftg_2015), [Pöcking districts](https://www.poecking.de/unsere-gemeinde/lernen-sie-uns-kennen/ortsteile). This calendar is descriptive and does not decide work permissions.

Hours use actual elapsed instants, split at local midnight, and retain original descriptions. `monthlySummary` filters the requested employer/month; `exportEmployerXlsx` creates a literal-text Jena or Seewiesen workbook. Adjacent intervals do not overlap; nested/cross-midnight intervals are checked. Shared DST/Tehran utilities are in `shared/datetime`.

## Private file storage

Private uploads use authenticated Vercel Blob `put/get` and owner-specific immutable operation keys, actual SHA-256, byte length, signature/type validation and checksum read-back. Distinct versions receive distinct keys; originals are preserved. Downloads require owner scope, use attachment-only headers and are never publicly listed. Missing private storage token fails closed. Root provisioning encountered an account usage-threshold restriction; no new store was created. Mocked byte tests prove local validation/retry boundaries, not a live Blob connection. See [Vercel private storage](https://vercel.com/docs/vercel-blob/private-storage) and [SDK get/put](https://vercel.com/docs/vercel-blob/using-blob-sdk).
